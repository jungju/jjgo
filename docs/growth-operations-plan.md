# JJGo 지속 개선·유입 운영 구축 계획

작성일: 2026-09-29 · 상태: 구축 계획, 미구현

2026-10-03 운영 기준 변경: 소유자 지시에 따라 매일 05:00 KST에 한·영 새 글 한 편을 작성·검증·발행하고 모델은 `gpt-6.1-sol / medium`으로 고정한다. 아래 초기 계획의 주 3편 한도와 Luna 선택은 이전 결정의 기록이다. 실제 예약 실행에는 최신 `docs/growth-operations.md`를 따른다.

## 1. 목표와 운영 결정

매일 한국 시간 오전 5시에 사이트 상태와 방문·검색 데이터를 확인하고, 동향을 조사한 뒤 근거가 있는 개선 작업을 수행한다. 좋은 글이 검색과 외부 채널에서 발견되고, 관련 글과 실제 프로젝트까지 읽히도록 운영한다.

- 실행 주기: 매일 05:00, `Asia/Seoul`.
- 예약: 기존 `jjgo` 예약을 통합 운영으로 전환한다. 별도 일일 예약을 겹쳐 만들지 않는다.
- 모델: `gpt-6-luna`, 추론 수준 `medium`을 초기 지정값으로 사용한다.
- 발행량: 초기에는 주 3편 이내의 새로운 주제, 한국어·영어 한 쌍을 한 편으로 계산한다. 매일 발행해야 한다는 기존 예약 조건을 수정한다.
- 작업량: 한 실행에서 신규 글 1편 또는 기존 글·사이트의 의미 있는 개선 1건을 기본으로 한다. 관련 내부 링크와 메타데이터 수정은 같은 작업에 포함한다.
- 알림: 발행·개선 완료, 장애, 권한 만료, 사용자 조치 필요 때 알린다. 변화 없는 점검과 중복 실행은 조용히 끝낸다.
- 초기 30일은 수집 정확성, 검색 발견 가능성, 주제 집중도, 배포 안정성을 우선한다. 방문자 증가율을 보장하거나 소수 방문으로 성공을 선언하지 않는다.

이 문서는 구현할 스킬·수집기·예약·유입 활동의 명세다. 문서 작성 자체로 스킬 설치, 예약 변경, 외부 게시를 실행하지 않는다.

## 3. 독자와 콘텐츠 전략

초기 독자는 AI를 실제 제품·업무에 적용하는 개발자, 기술 책임자, 소규모 제품팀으로 가정한다. 첫 4주 결과로 가정을 조정한다.

| 주제 축          | 독자의 문제                                    | 만들 콘텐츠 예시                       |
| ---------------- | ---------------------------------------------- | -------------------------------------- |
| RAG·평가         | 답변 품질과 실패를 어떻게 확인하는가           | 평가 설계, 실패 분류, 근거 확인 방법   |
| AI 제품·에이전트 | 새 기능을 어디에 적용하고 무엇을 검증하는가    | 특정 릴리스의 변화와 재현 가능한 사례  |
| 플랫폼·운영      | 개발 결과를 어떻게 배포·관찰·개선하는가        | 운영 점검표, 배포 실패 분석, 측정 방법 |
| 기술 에세이      | 기술 선택이 사람의 일과 판단에 무엇을 바꾸는가 | 영화의 장면에서 출발하는 구체적인 질문 |

위 예시는 작성 주제 후보이며 실적·경험의 주장이나 현재 인기 검색어가 아니다. 새 연구·실험 결과는 실제 실행 기록이 있을 때만 사용한다.

초기 편집 비중은 검색 질문을 해결하는 글 50%, 동향 해석 30%, 에세이 20%를 지향한다. 주간마다 기계적으로 비율을 맞추지는 않는다. 제목은 검색 가능한 구체적 문제를 담고, 본문에는 사례·비교·실행 가능한 설명 또는 고유한 관찰을 남긴다.

신규 글을 쓰기 전 기존 글 목록·대상 검색 의도·출처를 확인한다. 같은 질문에 이미 답한 글이 있으면 새 URL보다 보강을 우선한다. 한국어와 영어는 같은 사실을 전달하되 각 언어의 표현과 검색 의도를 따로 확인한다.

## 4. 측정 기반 구축

### 4.1 PostHog

운영 수집기는 `.env`의 `POSTHOG_PERSONAL_API_KEY`, `POSTHOG_PROJECT_ID`, `POSTHOG_APP_HOST`를 읽는다. 읽기 전용 범위를 유지하고 개인 키를 `NEXT_PUBLIC_*`에 넣지 않는다. `.env.local`과 값이 다르면 임의 우선순위로 처리하지 않고 설정 충돌을 보고한다.

수집 대상은 페이지·언어·유입 경로별 조회와 방문, 세션, 관련 글 이동, 프로젝트·컨설팅 이동이다. 읽기 완료나 문의 전환이 현재 수집되지 않으면 0으로 기록하지 않고 `NOT_INSTRUMENTED`로 남긴다.

필요한 행동 이벤트는 실제 UI와 기존 수집을 먼저 확인해 최소한으로 추가한다.

- `article_engaged`: 예를 들어 전경 활성 체류 30초 이상과 본문 50% 도달을 동시에 만족하는 세션별 최초 1회. 이 조건은 운영 정의이며 Google의 지표가 아니다.
- `related_article_click`: 출발 글·목표 글·언어.
- `consulting_cta_click`: 출발 페이지·버튼 종류. 클릭을 문의 완료로 해석하지 않는다.
- `share_click`, `rss_click`: 버튼 클릭만 측정하고 실제 공유·구독 완료라고 부르지 않는다.

로컬 개발·자동 점검은 수집을 비활성화하거나 명시적으로 분류한다. 운영자 제외 규칙은 확인된 ID·속성만 사용한다. Direct·데스크톱이라는 이유로 방문을 삭제하지 않는다. 원시 방문자 식별자와 개인별 행동은 Git 보고서에 남기지 않는다.

### 4.2 Google Search Console

1. `jjgo.io` 속성 존재와 소유권을 확인한다. 없으면 도메인 속성 등록 및 DNS 검증을 준비한다.
2. 읽기 전용 API 접근을 구성한다. 장기 로컬 실행에는 갱신 가능한 OAuth 인증 또는 명시적으로 권한이 부여된 서비스 계정을 사용한다.
3. 실제 sitemap 응답과 대표 URL을 확인한 후 등록 상태를 확인한다.
4. 날짜·페이지·검색어·국가·기기별 노출, 클릭, CTR, 평균 순위를 수집한다. 과도한 차원 조합을 피하고 페이지·검색어 분석을 나눈다.
5. 최신 확정 데이터를 기본으로 사용한다. 미완성 데이터·지연·API 결과 누락을 별도 상태로 기록한다.
6. 7일 비교와 28일 비교를 함께 보관한다. GSC 날짜 기준과 PostHog 시간대가 다를 수 있으므로 집계 구간을 명시하고 일별 값을 억지로 일치시키지 않는다.

PostHog와 Search Console은 측정 대상이 달라 수치 일치를 검증 목표로 삼지 않는다. GSC 검색어 결과는 익명화·결과 제한 등으로 모든 검색을 포괄하지 않을 수 있다.

### 4.3 운영 기록

사이트 자체는 기존 정적 구조를 유지한다. 별도 운영용 SQLite를 Git·배포 대상 밖의 로컬 데이터 폴더에 두고, 일일 요약 Markdown만 필요에 따라 저장한다.

| 기록      | 주요 필드                                                            |
| --------- | -------------------------------------------------------------------- |
| 실행      | run_id, KST 날짜, 시작·종료, 모델·추론 수준, 단계, 상태, 실패 이유   |
| 지표      | 출처, 수집 시각, 실제 집계 구간·시간대, 필터, URL·언어, 값, 완전성   |
| 주제      | 독자 질문, 후보 출처·발행일, 선정 근거, 기존 글 관계, 검색 수요 근거 |
| 작업      | 가설, 대상 URL, 이전 값, 변경 내용, 커밋, 배포 ID, 재평가일          |
| 유입 활동 | 채널, 글, 게시용 초안, UTM, 게시 권한 상태, 실제 게시 URL·시각       |
| 사용량    | 실행 시간, 관측 가능한 토큰·도구 호출·이미지 횟수, 금액 확인 여부    |

데이터 상태는 `OK / PARTIAL / UNAVAILABLE / NOT_INSTRUMENTED`로 구분한다. 실행 상태는 `SUCCEEDED / NO_CHANGE / BLOCKED / FAILED`로 구분한다. 데이터 미수집을 방문 0으로 대체하지 않는다. 원시 응답은 필요한 집계만 보관하고 기본 90일 이후 보존 필요성을 재검토한다. 운영 DB는 정기 백업과 복구 확인을 포함한다.

## 5. 검색과 외부 유입을 위한 구체적 작업

### 5.1 검색 발견과 클릭 개선

- 첫 점검: 실제 배포 HTML의 title, description, canonical, 언어 대체 링크, robots, sitemap, HTTP 상태, 모바일 렌더링, OG 이미지를 확인한다.
- sitemap에 제외된 경로가 있는 현재 정책의 이유를 확인한다. 샘플·중복·대체 URL은 자동으로 색인 대상에 넣지 않는다.
- 글마다 검색 의도 하나를 정한다. 제목과 첫 문단이 그 질문을 설명하고 본문이 실제 답을 제공하는지 검토한다.
- 노출이 있으나 클릭이 적은 글은 검색어와 제목의 불일치부터 확인한다. 무조건 자극적인 제목으로 바꾸지 않는다.
- 순위가 중간에 머무는 글은 누락된 설명·예시·최신 사실·관련 링크를 보강한다. 평균 순위만으로 수정 대상을 결정하지 않는다.
- 관련 글을 묶는 주제별 안내 페이지를 검토한다. 최소 3개의 충분한 글과 안내문이 있을 때 만들고, 빈 태그 페이지를 대량 생성하지 않는다.
- 기사 구조화 데이터는 실제 작성자·날짜·이미지와 일치할 때 적용한다. 수정 날짜는 실질적인 수정 시에만 변경한다.

검색 성과 초기 판단 기준 예시: 최근 28일 노출 100회 이상인 페이지부터 CTR 개선 후보를 검토한다. 이 숫자는 운영상 임시 기준이며 통계적 유의성이나 보편적 SEO 기준이 아니다. 표본이 적으면 내용 정확성·색인·내부 연결을 먼저 개선한다.

### 5.2 글 발행과 함께 준비할 유입 묶음

새 글마다 다음을 준비한다.

1. 제목·요약·대표 이미지·OG 미리보기.
2. 기존 관련 글 2~3개와의 자연스러운 내부 연결. 관계없는 글에 링크 수를 맞추지 않는다.
3. 한국어 짧은 소개 1개, 영어 짧은 소개 1개, 커뮤니티용 문제·사례 중심 소개 1개.
4. 해당 채널에 맞는 UTM URL과 실제 게시 여부 기록.
5. 7일 후 초기 유입 확인, 28일 후 검색·행동 재평가 일정.

UTM 예시: `utm_source=linkedin&utm_medium=social&utm_campaign=notes-<slug>`. 내부 링크에는 UTM을 붙이지 않는다. 캠페인 이름을 등록해 중복·오타를 막고, 실제 게시되지 않은 초안에는 유입 성과를 연결하지 않는다.

| 공개 GitHub 프로젝트   | 프로젝트 설명과 직접 관련된 글·재현 자료의 연결 검토        | 참조 유입·관련 자료 이동                        |
| 뉴스레터               | 초기에는 주간 요약 초안·웹/RSS 중심, 구독 수요 확인 후 검토 | 실제 동의 기반 구독이 생긴 뒤 측정              |

초기에는 소유 채널 1개와 관련 커뮤니티 1개에 집중한다. 게시 가능한 채널·계정이 확인되기 전에는 후보와 초안까지만 만든다. 사이트 배포 허용은 SNS 게시·댓글·메일 발송 허용을 뜻하지 않는다. 실제 게시 자동화를 켤 때 채널·계정·빈도·내용 범위를 명시적으로 정한다. 자동 댓글, 대량 DM, 구매 링크·백링크, 무관한 게시판 투고는 계획에 포함하지 않는다.

유입이 확인된 채널에는 좋은 글의 후속 사례를 보내고, 4주 동안 적합한 독자 유입이 확인되지 않는 채널은 빈도를 줄인다. 작은 표본의 전환율로 채널을 단정하지 않는다.

## 6. 동향 조사와 작업 선택

매일 GeekNews 최신 목록, 관련 공식 릴리스·기술 문서, 신뢰할 수 있는 원문을 조사한다. 검색 제안·Google Trends 등은 주제 후보 신호로 사용하며 절대 검색량으로 해석하지 않는다. 유료 키워드 도구는 초기 필수 구성에서 제외한다.

후보 3~~5개를 수집하고, 상위 후보 1~~2개의 원문을 충분히 읽는다. 출처의 주장·실제 확인한 사실·작성자의 해석을 구분한다. 원문 접근이 안 되면 근거 부족으로 표시한다.

선정 점수는 독자·사이트 관련성 0~~3, 수요 근거 0~~3, 기존 글과 다른 설명 가능성 0~~3, 근거·재현 가능성 0~~3, 작성 부담 0~3을 기록한다. 합계만으로 발행하지 않고 사실 확인과 독자 효용을 필수 조건으로 둔다. 이 점수는 편집 우선순위이며 검색 순위 예측 점수가 아니다.

작업 우선순위:

1. 사이트 접속·배포·추적 장애.
2. 잘못된 사실, 깨진 링크·이미지, 검색 차단 등 확인된 결함.
3. 이미 노출되는 글의 검색 의도·내용 개선.
4. 충분한 근거와 독자 질문이 있는 신규 글.
5. 내부 연결·RSS·채널 소개 초안·다음 작업 준비.

할 일이 없으면 NO_CHANGE로 끝낸다. 새 글 할당량을 채우기 위해 약한 주제나 이미 작성한 글을 재생산하지 않는다.

### 7.1 신규 운영 스킬 `jjgo-growth-ops`

설치 예정 위치: `C:/Users/jeong/.codex/skills/jjgo-growth-ops/SKILL.md`.

### 7.2 기존 `jjgo-blog-writing` 확장

- 기존 영화·GeekNews 무작위 경로는 유지한다.

## 9. 예약과 저비용 모델

### 9.1 선택 모델

기본 지정값은 `gpt-6-luna` + `medium`이다. 현재 앱 도구가 제공하는 사용 가능 모델에 포함되어 있고, 공식 모델 문서는 집중된 대량 작업에 효율적인 모델로 설명한다. 복잡한 장기 추론보다 정해진 수집·선정·편집·검증 절차에 맞춰 사용한다.

API 공식 표준 가격은 확인일 기준 입력 100만 토큰당 $0.10, 출력 $0.50이다. 이는 API 가격이며 Codex 구독 사용량·크레딧과 같은 가격 체계라고 가정하지 않는다. 검색·이미지 생성·재시도 비용도 별도다.

API로 별도 실행할 경우의 단순 계산 예시: 일일 입력 40,000·출력 8,000 토큰이면 텍스트만 약 $0.008/일, 30일 약 $0.24다. 실제 에이전트 실행은 여러 호출·추론·긴 문맥이 누적되므로 이 수치는 운영 견적이나 상한이 아니다. 현재 계획은 별도 유료 API 실행기를 만들지 않고 기존 앱 예약을 우선 사용한다.

첫 수동 시험 3회와 예약 시험 3회에서 실제 모델, 한·영 문장 품질, 사실 오류, 도구 호출, 실행 시간을 확인한다. 충분하지 않으면 발행 빈도·작업 범위를 먼저 줄이고 실패 사례를 남긴다. 비용이 더 높은 모델로 자동 변경하지 않는다.

### 9.2 모델 적용의 실제 제약

기존 예약은 heartbeat이며 현재 노출된 heartbeat 생성 필드에는 모델 지정 항목이 없다. 프롬프트에 모델 이름을 적는 것만으로 실행 모델이 바뀌었다고 간주하면 안 된다.

구축 시 기존 대상 채팅과 예약 UI의 모델 설정 지원을 확인한다. 지원되는 경로로 대상 실행을 `gpt-6-luna / medium`으로 지정하고 실제 실행 정보에서 확인한다. 지원되지 않으면 모델 고정 예약은 BLOCKED로 보고한다. 그때 사용자에게 독립 프로젝트 예약으로 전환하는 선택지를 설명하고, 명시적으로 선택된 경우에만 `model`·`reasoningEffort`를 지원하는 프로젝트 예약을 사용한다. 모델 고정만을 위해 임의로 새 예약·채팅을 만들거나 설정 파일을 직접 편집하지 않는다.

### 9.3 예약 변경 절차

1. 기존 `jjgo` 예약과 미완료 실행을 조회한다.
2. 새 운영 스킬·수집기·로컬 저장·모델 시험을 완료한다. 기존 06:00 예약이 계속 실행되는 동안 변경 작업이 충돌하지 않도록 전환 시점을 정한다.
3. 기존 ID와 대상 채팅을 유지해 이름을 `JJGo 매일 성장 운영`, 일정을 매일 05:00 KST로 갱신한다.
4. 프롬프트를 통합 운영 지침으로 교체하고 기존 사이트 발행 범위·알림 의도를 보존한다. 사용자가 명시적으로 설정한 다른 필드는 유지한다.
5. 실제 적용 시간대, 다음 실행 시각, 모델·추론 수준을 확인한다.
6. 수동 실행 후 다음 자연 예약 실행을 확인한다. 기존 06:00 발행이 남아 있지 않아야 한다.

예약 등록·변경에는 앱의 `automation_update`를 사용한다. 실행 호스트는 전원·앱·저장소·네트워크·인증이 유지되어야 한다. 05:00은 시작 시각이며 발행 완료 시각 보장은 아니다. PC가 꺼져 있던 날의 자동 소급 실행을 가정하지 않는다. 다음 실행은 누락을 기록하고 미완료 작업 하나를 우선 복구하며 과거 날짜만큼 글을 몰아 발행하지 않는다.

### 9.4 예약에 넣을 지침 초안

> JJGo 저장소에서 jjgo-growth-ops 스킬과 최신 운영 지침을 읽는다. 실행 잠금과 한국 시간 날짜별 작업 이력을 확인하고 미완료 작업이 있으면 먼저 복구한다. PostHog·Search Console과 공개 사이트 상태를 확인하되 결측을 0으로 해석하지 않는다. 사이트와 독자에 관련된 최신 동향과 원문을 조사하고 기존 글의 중복 여부를 확인한다. 장애 수정, 기존 글 보강, 신규 글, 유입 준비 중 근거가 가장 강한 작업을 정해 정해진 작업량 안에서 수행한다. 신규 글은 jjgo-blog-writing의 명시적 주제 경로로 한·영과 대표 이미지를 준비한다. 기존 사용자의 변경을 보존하고 필요한 변경만 검증·배포하며 정확한 커밋의 배포와 공개 URL을 확인한다. 외부 채널은 지정된 게시 권한 범위 안에서만 실행하고 미승인 채널은 초안으로 남긴다. 결과·출처·모델·측정 구간·배포·재평가일을 기록한다. 발행·개선 완료, 실패 또는 사용자 조치가 필요할 때 알리고 의미 있는 변화가 없으면 조용히 끝낸다.

스케줄과 모델은 실제 설정으로 별도 관리한다. 매 실행에서 정책·백로그 전체를 다시 작성하거나 저장소 전체를 분석하지 않는다.

### 9.5 비용·시간 통제

- 일반 점검·개선일 목표 20분, 발행일 목표 60분. 목표 초과 시 안전한 단계에서 기록·중단하며 강제로 불완전 배포하지 않는다.
- 초기 웹 검색 최대 6회, 심층 확인 원문 최대 5개를 운영 목표로 둔다. 부족하면 주제 범위를 줄이거나 다음 실행으로 넘긴다.
- 표지는 실제 신규 발행 때 1개, 결함이 있을 때 재생성 최대 1회. 표지 도구가 막히면 발행을 미완료로 남긴다.
- API 일시 오류 재시도 최대 2회, 같은 빌드 오류 수리 최대 2회 후 BLOCKED/FAILED와 근거를 기록한다.
- 위 숫자는 스킬의 운영 제한이다. 실제 런타임이 강제하는 토큰·시간·금액 상한과 혼동하지 않는다. 관측 불가능한 비용은 미확인으로 기록한다.
- 주간 집계에서 발행 한 편당 시간·사용량과 검색·이미지 호출을 검토한다. 초기에는 별도 유료 SEO·메일·광고 서비스를 도입하지 않는다.

## 11. 품질·배포·복구 조건

- 변경 작업은 적절한 관리형 worktree를 재사용하거나 필요한 경우 격리한다. 주 작업 트리의 미커밋 내용을 복사해 배포하지 않는다.
- 비밀 설정은 실행 호스트에서 안전하게 읽고 worktree·브랜치·정적 산출물에 포함하지 않는다.
- 공개 문구의 근거, 한·영 사실 일치, 출처, 제목의 약속과 본문, 이미지·alt·언어 전환을 확인한다.
- 관련 로컬 Next.js 가이드 확인 후 구현한다. `npm run lint`, `npm run build`, `npm run test:unit`, 필요한 포맷 검사를 통과해야 한다.
- 변경 페이지의 한·영 데스크톱·모바일 렌더링을 확인한다. 검사는 실제 실행 여부와 결과를 기록한다.
- 원격 변경을 확인하고 관련 변경만 커밋·푸시한다. 강제 push는 하지 않는다. 자동화끼리의 작업 잠금과 GitHub 배포 취소·경합 상태를 구분한다.
- 커밋·push·워크플로 성공만으로 완료 처리하지 않는다. 정확한 커밋의 배포 성공과 공개 글·표지·링크를 확인해야 `SUCCEEDED`다.
- 배포 전 오류는 변경을 격리한 채 중단한다. 배포 후 회귀는 해당 변경의 revert를 준비하고 검증해 복구한다. 다른 작업을 함께 되돌리지 않는다.
- 날짜·slug·source fingerprint·커밋·배포 ID를 저장해 재실행 시 다시 글이나 이미지를 만들지 않고 마지막 완료 단계부터 이어간다.

## 13. 성과 평가와 일일 보고

사업·독자 성과는 비브랜드 검색 클릭, 관련 주제 랜딩 방문, 글 참여, 관련 글 이동, 프로젝트·컨설팅 이동, 실제 확인 가능한 문의를 나눠 본다. 운영 성과는 중복 없는 실행, 확인된 배포, 출처 검증, 사용량·실행 시간이다. URL 수나 글 발행 수만으로 성과를 평가하지 않는다.

수정 전후 비교에는 기간·분모·절대값·동시 변경을 함께 적는다. 소규모 트래픽에서는 A/B 실험으로 유의미한 결과를 낼 수 있다고 가정하지 않는다. 지표 변화는 관찰 결과이며 수정의 인과 효과라고 단정하지 않는다.

결과 알림 형식:

```text
실행: 날짜 / 모델 / 상태
확인: 실제 집계 기간과 데이터 완전성, 주요 변화
선택: 오늘 작업과 선택 근거
반영: 글·개선 URL, 커밋과 배포 확인
유입: 준비 또는 실제 게시한 채널·UTM·URL
검증: 실행한 검사와 미확인 항목
다음: 재평가 날짜 또는 필요한 사용자 조치
```

첫 30일 목표는 정확한 측정·중복 없는 예약·검증된 글과 개선 이력·한 개 이상의 사용 가능한 유입 채널을 만드는 것이다. 트래픽 목표치는 내부 방문을 정리한 기준선과 검색 데이터가 쌓인 뒤 정한다.
